## Clarifications

### Session 2026-10-17 (planning against the code)

Binding for the plan.

- **There are no `metric`, `timeline`, `list`, `card_notice`, `choice_group`, `confirm`, `review`, `consent`, `connect_account` or `progress_steps` primitives on the wire.** The `render_*` tools build those patterns from atoms (`col`, `row`, `text`, `badge`, `divider`, `spacer`, `button`, `progress`, `table`, `form`, `connections`, `steps`, `chart`) plus 184's `headline`, `claim_card`, `claim_timeline`. The HUD look comes from restyling those atoms (text variants, badge, card-style `col`) in `@myguyze/ze-ui`; no new renderer types are added.
- **One conversation store, one reducer.** Today every `useChatWorkspace` instance keeps its own messages and parses frames, so the overlay and `/ask` do not share a thread's state. A per-thread store (`entities/conversation`) with a pure reducer owns `typing`, `token`, `message`, `edit`, `error`, `message_superseded` and `message_rollback`. One handler mounted in the shell feeds it and dispatches the presence events. `confirm_request`/`confirm_cancel` stay with the pending-confirmation store (one handler already), `trace_update` with the trace store, `refresh`/`notification` with invalidation. SC-001 means one owner of conversation state per frame; other slices may listen for their own reasons (the pending store acknowledging confirmations, World invalidation, the bell glance, 186's gate tracking reads the store), and each is named in a registry with its reason.
- **"Why?" cannot name the exact tool call yet.** Message components carry no call index (`ToolCallTrace.call_index` exists; components do not point at it). "Why?" opens the reply's trace module at the section for the module's origin: Routing for a preset reply (`method: preset`), Tools (render and show rows highlighted) otherwise. The per-module link is a backend gap recorded for 194 (a `source_call_index` on top-level components).
- **Onboarding starts on the server.** On connect, `start_if_needed` sends the onboarding view as a `message` frame on thread `onboarding:<session_id>` with `OnboardingMeta { session_id, completed }` (no step data). Ask opens that thread when the frame arrives and no other turn is running, and Presence shows "getting to know you" until `completed`. No stepper: the meta has no steps to draw. The `onboarding` command is not sent by the client.
- **Workspace attach moves to the Ask bar.** The old composer's paperclip (`placeWorkspaceFile`, chips, `workspace_placed` on the next message, phase 115) is the only way to hand Ze a file; the Ask bar gains it on `/ask` and in the overlay.
- **Confirmations pause the delivery watchdog.** Today the watchdog stops while a confirmation card is open (the card clears the thinking flag) and restarts on answer; the reducer models this as `paused`/`resumed` so a 15-minute card never reads as an undelivered reply.
- **Reply feedback stays on the reply.** The latest reply keeps a compact thumbs pair (the trace module head also has them), so phone feedback is one tap.
- **`pages/chat` is unrouted dead code** (183 removed its route); it is deleted with `widgets/chat-workspace`. `shared/effects/spotlight.tsx` is used by `widgets/onboarding-wizard` (first-run configuration); the wizard switches to the ze.css background in this phase so the effects can go.
- **Deleting the `/jarvis` composition** removes `pages/jarvis/model/compose.ts`, `views/AssembleView.tsx` and its `/jarvis` sub-route; the `Component` type `hud/Cards.tsx` imports moves into `Cards.tsx`. The rest of `/jarvis` stays until 193.

### Session 2026-10-18 (user request relayed by the Maestro: trace instruments; displaced window)

The user asked: "we should incorporate the trace panel into some widgets and infos GMUNK style for the assemble/ask screen. We could draw cool stuff from trace." Binding for the plan:

- **The trace becomes instruments (US8), drawn only from data the client already receives.** `MessageTrace` (REST `getMessageTraces`) and the `trace_update` frames (partial and final) are the only sources. No new backend in this phase. Instruments: Signal path, Routing, Memory used, Tools and delegates, Judgments, Readouts (latency, model, System One requests and tokens, compaction), Reversal track. They replace the plain trace sections. Rows with no instrument form stay as readout rows in the same rail: Skills, Sources, Workspace, Conductor, Confirmations, Screen resolvers, Feedback.
- **Layout: a rail, not a frame around the answer.** On desktop `/ask` the instruments sit in the right rail for the selected reply, calm by default: the Signal path and one readout line per instrument. An instrument expands on hover, focus or click. In the overlay and on phones, "Why?" opens the same rail as a sheet. Framing the answer on the canvas with instruments would compete with the answer's own modules. Reduced motion: no light sweep, no draw-on; states change in place.
- **Each instrument shows only what the data proves:**
  - **Signal path.** Partial frames arrive today only after `embed_route`, `resolve_screen`, `fetch_context` (only when memory was retrieved), `choose_tier` and each tool end, then the final trace. The strip draws exactly those stages, in pipeline order: screen (only when the turn had screen context; `resolve_screen` runs before routing), route, memory, tier, tools, reply. Each stage lights when its frame arrives, with a "+1.2 s" readout per tick. Memory (only when chunks were retrieved) and tier (only for a single-agent turn whose agent declares `model_simple`) may never arrive, so no "waiting" tick is drawn for them. While streaming, the strip shows the lit stages plus the reply as the pending end. The memory tick carries the chunk count. That readout is the arrival time on the client after the send, labelled as arrival. When the final trace lands, the strip settles and shows the server's `total_duration_ms`. Preprocess, skills, correlate, surface, synthesize and memory write send no frame, so they are not drawn. A history reply shows the settled strip only.
  - **Routing.** `confidence` and `score_gap` mean different things on different routing paths (`ze_core/routing/router.py`), so the bar is labelled by its source:
    - `embedding` with the `agent` judgment absent or not consumed: "E5 score", plus a ghost bar for the runner-up at `confidence − score_gap`. Only this path has a runner-up, and the runner-up's name is not on the trace.
    - `embedding` with the `agent` judgment consumed (Choice trust or decompose, the shipped config): "Choice confidence" (the peakedness). No ghost: the E5 gap does not apply.
    - `screen`, `preset`, `forced`, `open_query`: "fixed". 1.0 is a constant, not a measurement, so there is no bar and no ghost.
    - `haiku`: "Haiku", no ghost.
    - `fallback`: "fallback", no bar. Method in words. Compound subtasks as a fan. The System One routing Choice (judgment `agent`, plus `multi_specialist`, probabilities per option) as needles. The tier (`tier`, `decided_by`, `model`) and the `needs_deep_reasoning` probability. "Asked from / Asked about" (195) as a coordinate readout: place, route, subject. No threshold line: the calibrated bars are not on the trace.
  - **Memory used.** Drawn from the committed trace only, because live memory partials carry no `extraction_confidence`. While streaming, the Signal path's memory tick shows the chunk count. A constellation: x = relevance (`score`), y = extraction confidence. A chunk without a confidence sits on a dashed floor line. Glyph by `source` (fact, episode, profile). Hover or focus shows the text. A ranked list is the phone and screen-reader form.
  - **Tools and delegates.** One lane per agent (the main agent first, delegates below). Calls in `call_index` order, widths by `duration_ms`. Each lane is laid end to end on its own axis; lanes share no time axis and are never compared with `total_duration_ms`. A `delegate_to_agent` call's duration includes the delegate's own calls, which appear in the delegate's lane, so it is marked "includes the delegate's calls". Parallel fan-out also overlaps in real time. The caption says "order and duration per lane; start times not recorded". Irreversible writes are marked. Each call's `gate` (`approved`, `denied`, `refused`, `expired`) is a tick on that call. Write confirmations stay in the Confirmations readout row, because their rows carry no `call_index`. Failed calls are dim with "failed". **Live partial tool frames carry placeholders** (`duration_ms: 0`, `success: true`), so while streaming a call shows only "returned". Duration and success come from the final trace.
  - **Judgments.** Grouped by surface through a closed map of question ids: routing (`agent`, `multi_specialist`), tier (`needs_deep_reasoning`), skills (`skill`, `needs_skill`), intake (`commitment`, `family`, `biography`, `is_open_concern`, `explicit_declaration`, `resolves_existing`). Unknown ids show the humanised id. Choice: probability bars with the answer lit. Noul: one gauge. Score: the value. Consumed, or skipped with the reason in words. The synthetic `intake_outcome` row (kind `choice`, an answer string and no probabilities) is rendered before the generic Choice renderer. Its answer (`<kind>:<reason>[:<link>]`) shows the decision in words: one of the seven `OutcomeKind` values (`persist_fact`, `resolve_loop`, `create_loop_declared`, `create_loop_suspected`, `link`, `hold`, `fallback`) with its reason and link kind (`reminder`, `goal`, `reminder+goal`). Hold reasons are partly dynamic (`<choice>_not_created`) and fallback reasons are skip reasons, so unknown reasons are humanised. No bar line (see Out of Scope).
  - **Readouts.** Dot-matrix `total_duration_ms`; the main model from `tier.model`; "System One: N requests, X ms, Y input tokens". Each batch copies its request's latency, model and tokens onto every row, so this counts one request per surface group (the rows of a group carry the same values) and skips `intake_outcome`; a compaction mark ("earlier turns folded into a summary", span) and "resumed with a recap". No token, cost or context-window readout for the main model, and no money at all: the trace carries neither.
  - **Reversal track.** `rollback.entries` in reverse call order with the undo tool's effect and the outcome in words; the message's rollback state.
- **Displaced window.** Since `main` f75e6848, a window replaced by another (close code 4000) stops reconnecting and sets `useWsStore.displaced`; it takes over on focus. One connection state, `online | displaced | offline`, is derived from `useWsStore` and replaces the separate offline checks. While it is `displaced`:
    - every place shows one line, "Ze is open in another window · Use here"; "Use here" reconnects through a new `takeOver()` in `shared/api/ws-client`;
    - presence dispatches nothing, so the orb stays idle (today `ws_closed` turns it to error, "Offline");
    - the connection dot reads "Open in another window";
    - the Ask bar, the overlay and World's write controls use that line instead of "Ze is offline".
  The existing focus takeover reconnects as soon as the window gains focus, so "Use here" mainly serves a window that is visible but not focused (side by side).

## Overview

Ask is where the user talks to Ze, at `/ask` and `/ask/:threadId`. Every reply assembles as HUD modules on a 12-column canvas, flying in from the orb 80 ms apart; the reply text is the Sentence module; the trace is a module beside the answer, one "Why?" away from any module. It replaces the interim Ask section (the old chat page), the trace side panel, the session list in the nav, the confirmation card, retry and the old onboarding chat entry. It also gives the contextual overlay from phase 183 the same assembly: the user decided (2026-10-17, 183 OQ-2) that the Ask bar on any other screen opens an overlay where the answer arrives in place, and that the exchange is a real Ask thread. Phase 183 built the overlay shell and thread behaviour; this phase renders the overlay's replies with the same canvas, trace chip, confirmation card and Retry as `/ask`.

## Modules

- **Contextual overlay** (every place except `/ask`): the 183 `AskOverlay` shell (thread = the session selected in Ask, `context.screen` per message, "Open in Ask", "New chat") now renders each reply as the Assemble canvas in compact form (spans collapse to 12, instrument index kept), with the cascade from the Presence orb's position, the trace behind a chip per reply, the confirmation card in place for the overlay thread, and Retry on the latest reply.

- **Left rail**: Presence (orb phases driven by the turn: listening → thinking on `typing` with `typing.text` as the phrase → speaking on first `token` → done on `message`; `assembling` while components cascade; "getting to know you" during onboarding), **Try** chips (keys 1–3): "What's slipping?" (`context.compose="slipping"`), "What should I decide today?" (`decisions`), "How is <goal> going?" (`topic` = the active goal with the most recent progress, from the goals list; hidden when there is none), and **Sessions** (history, search: `listSessions`, `searchSessions`).
- **Canvas**: Sentence (tokens stream in; decode on settle), then one module per top-level component: the 184 primitives (`headline` as the dot-matrix headline, `claim_card`, `claim_timeline`) and every existing atom restyled (col, row, text, badge, divider, spacer, button, progress, table, form, connections, steps, chart), which restyles every `render_*` pattern built from them. Instrument index = position in the answer (decision 9). Pin and dismiss per module.
- **Trace instruments** (US8): the trace module becomes a rail of HUD instruments for the selected reply: Signal path (lit live as frames arrive), Routing, Memory used, Tools and delegates, Judgments, Readouts, Reversal track. Skills, sources, workspace, conductor, confirmations, screen resolvers and feedback thumbs (in the head) stay as readout rows. Desktop: right rail. Overlay and phone: a "Why?" sheet.
- **Displaced window**: "Ze is open in another window · Use here" on every place while another window holds the connection.
- **Confirmation card**: in place on `confirm_request` (write: one row per item with the imperative effect phrase and an editable body when `editable_field` is set; budget; held with the source run named; prompt: title as the question and actions as command chips); Approve/Deny send `confirm`; prompt buttons send `action`; `confirm_cancel` closes it everywhere. The same component renders in World/Doing Needs you.
- **Feedback**: a compact thumbs pair on the latest reply (and in the trace head).
- **Retry**: on the latest reply, two-step undo-plan consent (`retry_eligibility`, `confirmed_plan`), `message_rollback` updates the rollback section, `message_superseded` swaps the reply; disabled with its reason when history is unavailable.
- **Onboarding**: the server starts it on connect (thread `onboarding:<session_id>`); Ask opens that thread; Presence says "getting to know you" until `completed`; forms and choices are primitives submitting `component_submit`.

## User Scenarios & Testing *(mandatory)*

1. **A full turn streams with a progressive trace (P1).** Test: WS frame reducer over `typing`, `token`, `trace_update` (partial), `message`, `edit`, `error` (busy → "Ze is still working on the last one" with Cancel); orb phase sequence.
2. **A preset answers with backend modules (P1).** Tapping "What's slipping?" sends `message` with `context.compose`; the canvas renders the reply's `headline`, `claim_timeline`, `claim_card`s in order with posture visuals; no client composition code exists (`rtk proxy grep compose.ts` empty).
3. **"Why?" lands on the trace section for the module's origin (P2).** Test: a preset reply's module opens Routing; a rendered module opens Tools with the render rows highlighted (per-call link deferred to 194).
4. **A write confirmation round-trips (P1)**, incl. editable body and deny; `confirm_cancel` closes it.
5. **Retry with undo (P1)**: plan shown, confirmed, `message_rollback` reflected, reply swapped.
6. **Ask in place (P1).** From `/doing/goals/g1` the Ask bar opens the overlay; the reply assembles there as modules (same component as `/ask`, compact); "Why?" opens its trace chip; a `write` confirmation for that thread renders in the overlay and round-trips; "Open in Ask" shows the same thread with the same modules. Test: overlay renders the canvas for a reply with components; confirmation for the overlay thread renders inside it, not as a separate card.
7. **Phone (P1)**: Presence compact → Try chips → canvas (spans collapse to 12, timeline omitted) → Trace behind a chip.
8. **The trace reads as instruments (P2).** During a turn the Signal path lights route → memory → tier → tools as their frames arrive, with arrival readouts, and settles to the server total on the final trace. For a finished reply: the Routing needle and runner-up bar, the memory constellation (hover shows the claim; list on phone), the tools lanes with irreversible and gate marks, judgment gauges with consumed or skip reasons, readouts and the reversal track render from a fixture trace. Nothing the trace lacks is drawn (no threshold line, no main-model cost, no overlap). Reduced motion: no sweep.
9. **A second window (P2).** Opening Ze in another window shows "Ze is open in another window · Use here" in the first, visible but unfocused, window; the orb stays idle and the connection dot says "Open in another window"; "Use here" (or focusing the window) takes the connection back; the Ask bar is disabled with that line meanwhile.

## Out of Scope

- Voice (193). Backend changes: none. Gap found while planning, for 194: top-level components carry no tool `call_index`, so "Why?" cannot link one module to one call.
- Trace data the instruments would need but the backend does not send (proposed as phase 187b, see the plan): a progress frame for every graph stage with server-side ms; the E5 shortlist with scores (`RoutingEnvelope.raw_scores` exists but is not on the trace); the calibrated bar and surface on each judgment; per-turn tokens and cost for the main model (`llm_cost_log` is keyed by session only); context-window fill (tokens used against the window); tool call start offsets, plus real `duration_ms` and `success` on live partial tool frames.
