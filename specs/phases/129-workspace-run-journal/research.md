# Phase 0 Research: Workspace Run Journal

No items in the plan's Technical Context are marked `NEEDS CLARIFICATION` — the
spec pins the four control-plane paths verbatim and the existing Phase
115/116 code fixes language, framework, and deployment target. This document
instead resolves the design choices the spec explicitly deferred to plan time
("Exact retention is a plan-time choice") and records the alternatives
considered for each.

## Decision 1: The run id is mind-generated, not sidecar-generated

**Decision**: `POST /run` accepts an optional `id` (UUID) in the request body.
`ze-api` always supplies its own `workspace_runs.id` (already generated by
`WorkspaceStore.insert_in_progress_run` before the sidecar call). The sidecar
uses that id as the journal key; if absent (e.g. a manual/debug call), it
generates one and returns it.

**Rationale**: The alternative — sidecar generates the handle and returns it,
mind stores it in a new `sidecar_run_id` column — creates two ids for one run
and a translation table for no benefit: every caller of the sidecar in this
codebase is `ze-api`, and `ze-api` already mints a UUID for the mind-side row
before it knows whether the run will finish inside the short wait (Phase 116's
`_run_and_maybe_detach`). Reusing that id end-to-end means `GET /runs/{id}`,
`/runs/{id}/events`, and `POST /runs/{id}/cancel` are addressable with the
exact id already shown to the user in "[still running] run `{recorded.id}`"
(`tools.py`), with no lookup step and no risk of the two ids drifting.

**Alternatives considered**:
- Sidecar-generated handle + `sidecar_run_id` mapping column — rejected as
  unnecessary indirection for a single-caller system (adds a nullable column
  and a translation step for zero behavioral gain).
- Reuse the *conversation* `thread_id` as the handle — rejected: multiple runs
  can occur on one thread over time (sequentially, never concurrently per
  FR-007), so it is not a stable per-run identity.

## Decision 2: The journal is in-process memory, not a sidecar-local database

**Decision**: `supervisor.py` keeps a `dict[UUID, JournalEntry]` in memory.
No SQLite, no file-backed journal.

**Rationale**: FR-009 explicitly forbids SQLite (or any VFS) as the
filesystem, and the sidecar has never had a database — Phase 115 fixed the Fly
volume as file truth and nothing else. The run journal only needs to survive a
**mind** restart, not a **sidecar** restart (Edge Case: "What happens if the
computer is unreachable after restart? The run fails in plain language" — a
lost sidecar process is an accepted terminal-failure case, not a case the
journal needs to survive). An in-memory dict is sufficient and keeps the
sidecar exactly as unprivileged and stateless-except-the-volume as Phase 115
specified.

**Alternatives considered**:
- Write journal entries to a file under `/workspace/.runs/` — rejected: would
  survive a sidecar restart, which the spec does not require (Edge Case 3
  explicitly accepts the loss), and would consume the storage ceiling for
  transient run bookkeeping instead of user files.
- A tiny embedded KV (e.g. `shelve`) — same objection as SQLite: adds a second
  persistence primitive FR-009's spirit (no VFS, no second backend) argues
  against, for a requirement the plain dict already satisfies.

## Decision 3: Retention — bounded count, not pure TTL

**Decision**: The journal retains the current running entry (if any) plus the
last 5 terminal entries, evicting the oldest terminal entry once a 6th is
added. There is no separate time-based expiry.

**Rationale**: One run at a time is a hard rule (FR-007), so at any instant
there is at most one "running" journal entry; "5 terminal entries" is not a
scale concern (this is a single-user, single-workspace system — Scale/Scope),
it is a correctness margin against the realistic retry window: a mind restart,
reconciliation on the next startup, and the operator re-running
`GET /runs/{id}` a couple of times while debugging a deploy. A pure count
bound is simpler to reason about and test than a wall-clock TTL, and it can
never grow unbounded even if the mind never calls back (satisfying "MUST NOT
dump an unbounded wall of text" in spirit — bounded *entries*, not just
bounded *text per entry*, which FR-004/Edge Case on large output already
covers separately via `OUTPUT_PREVIEW_CHARS` + spill-to-file).

**Alternatives considered**:
- TTL only (e.g. 1 hour) — rejected: unbounded if the mind is down longer than
  the TTL but the sidecar keeps accepting new runs from an operator debugging
  directly against the sidecar; a count bound caps memory regardless of
  elapsed time.
- Retain forever until explicit dispose call — rejected: no caller in this
  codebase ever disposes a handle (no such tool/route is specced), so "forever"
  is a slow leak across long-lived deploys.
- Retain only the single most recent terminal entry — rejected: too tight a
  margin for Edge Case 2 ("a detached run that already finished during the
  restart window") stacked with an operator poking `GET /runs/{id}` — 5 gives
  headroom without meaningfully changing memory footprint (previews are
  already capped at `OUTPUT_PREVIEW_CHARS`).

## Decision 4: `GET /runs/{id}/events` streams newline-delimited JSON, not SSE

**Decision**: The events endpoint returns `text/event-stream`-free, plain
chunked `application/x-ndjson`: one JSON object per line, each
`{"type": "stdout"|"stderr"|"exit", "seq": int, "data": str, ...}`. Already-
buffered events are replayed first, then live events are yielded as they
arrive; the stream closes once the `exit` event has been sent. A caller that
connects after the run is already terminal gets the full buffered sequence
followed immediately by `exit`, satisfying "watching after the fact still
works" (User Story 2, Acceptance Scenario 2).

**Rationale**: SC-002 requires output to arrive before the command exits, i.e.
a streaming (not buffer-then-return) response — `httpx`'s
`AsyncClient.stream()` on the mind side and FastAPI's `StreamingResponse` on
the sidecar side both support chunked transfer without extra dependencies.
NDJSON is simpler than SSE framing (`event:`/`data:`/blank-line) for a
same-process-family internal contract with exactly one consumer
(`ze-api`'s `RunWatcher`), and matches the plain-JSON style the rest of the
sidecar API already uses (`main.py`'s other routes are all plain JSON).

**Alternatives considered**:
- Server-Sent Events — rejected: no browser `EventSource` client exists in
  this phase (chat streaming is explicitly a later layer, and the immediate
  consumer is `httpx` on the mind, not a browser), so SSE's extra framing buys
  nothing yet; NDJSON keeps the door open for wrapping it in SSE at the
  ze-web layer later without changing the sidecar contract.
- A WebSocket — rejected: adds a second protocol to a service that is
  otherwise plain HTTP, for a one-directional (server-to-client) stream that
  chunked HTTP already serves.

## Decision 5: FR-007's refusal is enforced at the mind, not only the sidecar

**Decision**: `workspace_run`/`workspace_run_skill_script` call
`WorkspaceStore.list_in_progress()` (already exists, unused for this purpose
today) before calling the sidecar at all. A non-empty result raises the
refusal with the running row's `command`/`id`, matching FR-007's wording ("The
refusal MUST name the running handle and command") without a round trip. The
sidecar's own one-slot guard (Decision 3's "at most one running entry") stays
as the authoritative backstop for a race (two mind processes, or a manual
sidecar call) but is not the primary UX path.

**Rationale**: Phase 116 already tried to close this at the sidecar layer
(the old `_lock`/409 `busy` path) and it was explicitly named as unfinished
(spec's User Story 4: "which the follow-through implementation left
unfinished"). The gap was that a 409 from the sidecar surfaces as a bare
`WorkspaceBusyError` with no handle/command context by the time it reaches the
tool caller. Checking `list_in_progress()` first means the refusal message can
be built from data the mind already has (the in-progress `workspace_runs` row
carries `command` and `id`), with zero sidecar round-trip for the common case,
and it applies uniformly to conversation, user-initiated, and unattended
origins (FR-007) since all three paths go through the same tool functions.

**Alternatives considered**:
- Rely solely on the sidecar's 409 and enrich the exception with a follow-up
  `GET /runs` lookup — rejected: an extra round trip on every busy refusal,
  and duplicates state the mind's own `workspace_runs` table already has
  authoritative(-enough) visibility into for this purpose.

## Decision 6: `SidecarPollCompletionSource` is deleted, not extended

**Decision**: The `RunCompletionSource` protocol and its
`SidecarPollCompletionSource` implementation (`followthrough.py`) — which
polls `/stat`'s `busy` flag and fabricates a `WorkspaceRunResult` with the
"(output unavailable...)" placeholder — are removed. `RunWatcher.reattach()`
instead calls `GET /runs/{id}` directly (via a new `WorkspaceClient.get_run()`)
and, if still running, resumes watching `/runs/{id}/events` for the terminal
event.

**Rationale**: The entire reason `SidecarPollCompletionSource` existed was
"Phase 115's sidecar contract has no per-run status/output lookup, only
`/stat`'s `busy` boolean" (its own docstring). This phase adds exactly that
lookup — keeping the old fallback around as dead code (or a further fallback)
would reintroduce the placeholder path FR-003 forbids ("A restart MUST NOT be
sufficient cause to replace the result with an 'output unavailable'
placeholder when the computer still has the run"). The one case the old code
handled — the sidecar itself being unreachable — is exactly Edge Case 3, which
the plain "run fails, in plain language, mind does not invent success" path
in `reattach()`'s error branch already covers without a placeholder.

**Alternatives considered**:
- Keep `SidecarPollCompletionSource` as a fallback for when `GET /runs/{id}`
  itself errors — rejected: `GET /runs/{id}` erroring (connection refused,
  5xx) *is* Edge Case 3 ("the computer itself restarted and lost the
  in-flight process"); the correct response is the plain-language failure the
  edge case specifies, not a second polling loop guessing from `/stat`.
